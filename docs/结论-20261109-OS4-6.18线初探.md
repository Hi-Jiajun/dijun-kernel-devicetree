# 结论 2026-11-09：OS4（Android 17 / 6.18.21）线初探

## 能解包、能编，但 ABI 复现比 6.6 难

OS4 备份的内核是 `6.18.21-android17-5-g1d099fcb35e0-abogki538445360-4k`，clang 22.0.1 (r584948c)。这条线的可行性比 6.6 好的一点是：**源码是公开的**（`android17-6.18`，`-2026-06` 分支正好是 6.18.21），配置也能直接从 `boot_a` 抽出来（8,462 行），OS4 的模块也能从 `super.img` 里取（`vendor_dlkm` 199 个、`system_dlkm` 210 个，用自编的 `fsck.erofs` 解出）。

本轮已完成的离线动作：

1. 克隆 `kernel/common` 的 `android17-6.18-2026-06`（6.18.21，AOSP 公开分支）；
2. 稀疏克隆 `prebuilts/clang/host/linux-x86` 的 `android17-release`，取到 `clang-r584948`（clang 22.0.1）；
3. 用 OS4 config + 4,068 个模块导入符号的白名单，构建出 `out618/vmlinux`（exit 0）；
4. 用 OS4 的 404 个模块跑 `abi-gate`：**内核符号 CRC 不符 9,723 条**，基线不通过。

## 为什么不通过

6.18 的 CRC 生成机制换了：`CONFIG_GENDWARFKSYMS=y`、`CONFIG_EXTENDED_MODVERSIONS=y`，CRC 由 `scripts/gendwarfksyms` 从 DWARF 计算，而不是 6.6 的 genksyms 解析声明文本。这意味着 CRC 对**源码提交、编译器版本、调试信息与类型细节**都更敏感。我们只对上了版本号（6.18.21），没对上 `g1d099fcb35e0` 这个提交——它在公开镜像里不存在，`vendor_dlkm` 的 vermagic 还是 `maybe-dirty`，说明厂商那份树带本地改动。这种情况下 9,723 条不符是预期结果，不能据此否定 6.18 线。

另外 `CONFIG_MODULE_SIG_PROTECT_LIST="protected_module_names_list"` 在纯 kbuild 下需要一个文件，Kleaf 才生成；补一个空文件即可继续。

## 对路线的影响

- OS4 的配置里 **`CONFIG_CGROUP_PIDS=y`**，OH 需要的 pids 控制器本来就有，不必自编内核；`CGROUP_DEVICE`、`PID_NS` 仍是 n。
- 要在 6.18 上自编内核并加载 OS4 原厂模块，需要拿到 `g1d099fcb35e0` 对应的源码或等价补丁集（厂商 dirty 树），否则 gendwarfksyms 的 CRC 对不齐。
- 因此 6.18 线目前只完成了"能解包、能编、能跑 gate"的可行性验证；ABI 复现还缺关键输入。

## 追查 `g1d099fcb35e0` 的结果（2026-11-09）

- AOSP `kernel/common` 全部分支/标签里都没有这个提交（`/+/g1d099fcb35e0?format=JSON` 返回 "Object is not found"；本地浅克隆的历史里也没有）。
- GitHub commit 搜索只命中一个无关仓库；MiCode 的开源索引仓库里没有 dijun/XRing O1 的 6.18 条目；SWH/镜像也没有新的 6.18 树。
- 结论：这是**厂商私有树**的提交（`vendor_dlkm` 的 `maybe-dirty` 也印证了本地改动），公开渠道拿不到。

## 判定细化：GKI 模块也对不上

分别跑 gate：

| 模块集 | 模块数 | 内核符号 CRC 不符 |
| --- | --- | --- |
| `system_dlkm`（GKI） | 210 | 5,362 |
| `vendor_dlkm`（厂商） | 194 | 4,361 |

连 GKI 那部分都对不上，说明 `gendwarfksyms` 的 CRC 对源码提交/补丁/编译器极其敏感；只对上 6.18.21 版本号没有用。

## 路线含义

- OS4 官方内核已经带 `CONFIG_CGROUP_PIDS=y`，OH 需要的 pids 不用自编；`CGROUP_DEVICE`/`PID_NS` 要改则必须解决上面的源码缺口。
- 6.18 自编内核在拿到厂商源码/补丁集前不可行。可行的替代是：OS4 stock 内核 + 用户态方案；或退回 6.6.118 线只加 `PID_NS`。
- AOSP 官方支持表显示 Android 17 支持 6.18/6.12/6.6 三代内核——厂商在 OS4 选择 6.18.21，不代表 6.6 线在 Android 17 上不可用，但那是另一套 vendor/模块组合。

## 一个未采用的思路（记录风险）

理论上可以后处理自编内核的 CRC 表，把导出符号的 CRC 改成原厂模块期望的值，从而绕过 `__versions` 校验；但只要类型/布局有实质差异就会在运行时炸，而且 6.18 的 `EXTENDED_MODVERSIONS` 让 CRC 表布局更复杂。仅作为最后手段记录，不建议用于日用。

## 突破：stable 模式一开，CRC 全对（2026-11-09 晚）

问题不在源码提交，而在构建参数：6.18 的 `scripts/Makefile.build:198` 用 `$(if $(KBUILD_GENDWARFKSYMS_STABLE), --stable)` 决定 gendwarfksyms 是否按 kABI 稳定性规则算 CRC，Kleaf 构建时会传这个变量，我们纯 kbuild 没传。

用同一份 AOSP 6.18.21 源码、同一 OS4 config、同一 clang 22，只加 `KBUILD_GENDWARFKSYMS_STABLE=1` 重编（`out618s/`）：

| 模块集 | 模块数 | CRC 不符 |
| --- | --- | --- |
| `system_dlkm`（GKI） | 210 | **0** |
| `vendor_dlkm`（厂商） | 194 | **0** |
| 合计 | 404 | **0** |

也就是说：**AOSP 公开的 6.18.21 + OS4 原厂 config + clang 22 + stable 模式，可以完全复现 OS4 原厂模块的 CRC**，不需要厂商私有提交。之前 9,723 条的结论作废。

剩余未闭合项是"符号提供方"而不是 CRC：404 个模块里 62 个仍有无法解析的导入，主要是 Rust 内核符号（`rust_binder.ko` 缺 60 个 `_RNv...`，我们的 config 因为没装 Rust 工具链把 `CONFIG_RUST` 丢了）和 vendor-core 符号（`memcpy_s`、`cdev_tevent_*`、`vote_mng_*`、`walt_*`），后者大概率在 OS4 的 `vendor_boot` 模块里（本地没有 OS4 vendor_boot）。

## 功能开关在 6.18 上的验证（stable 模式）

| 变体 | 配置 | CRC 不符 | 判定 |
| --- | --- | --- | --- |
| out618s | OS4 原样 | 0 / 404 模块 | PASS |
| out618_pns | +`PID_NS=y` | 0 | PASS（ABI 安全） |
| out618_cdev | +`CGROUP_DEVICE=y` | 6,377 | FAIL（模块会拒绝加载） |

结论与 6.6.118 一致：`PID_NS` 可以加，cgroup 控制器加不了——新增控制器会改变 `cgroup_subsys_id`/`CGROUP_SUBSYS_COUNT` 相关声明，gendwarfksyms 的 CRC 随之大面积变化。OS4 原厂已经带 `CGROUP_PIDS=y`，所以 pids 不需要自编；`CGROUP_DEVICE` 需要整套模块重编才能用。

## 6.18 自编内核剩余的缺口（都不是 CRC）

1. **Rust**：OS4 config 里 `CONFIG_RUST=y`、`BINDER_RUST=m`，我们的纯 kbuild 没装 rustc 1.91 工具链，`olddefconfig` 把 RUST 关掉了，直接后果是 `rust_binder.ko` 缺 60 个内核 Rust 符号。补 rustc（Android Rust Toolchain 15551131）后可以恢复。
2. **OS4 vendor_boot 模块**：62 个模块缺 `memcpy_s`、`cdev_tevent_*`、`vote_mng_*`、`walt_*` 等 vendor-core 符号，这些应由 OS4 的 `vendor_boot` 里的模块提供；本地 pdump 的 vendor_boot 是 6.6.118（备份混合），需要 OS4 OTA 包或设备上的 OS4 vendor_boot。

补齐这两项后，6.18 线就能做到"自编内核 + 原厂全套模块"，且可以加 `PID_NS`；`CGROUP_DEVICE` 仍然要整套模块重编。

## vendor_dlkm 源码与"二进制绕过"（2026-11-09 晚）

**源码**：MiCode 的开源索引里 dijun 只有 `dijun-v-oss`（Android V / 6.6.30），没有 6.18；OS4 的 `vendor_dlkm` 模块检查到 `license=GPL`，按 GPLv2 厂商有提供对应源码的义务，这是要源码的正式依据，但公开渠道目前拿不到。社区渠道（Telegram 提取包等）只发内核 Image 和 dtb，不发模块源码。

**二进制绕过已实现并离线验证**：新增 `patch-module-crc.py`，解析 6.18 的 `__version_ext_crcs`/`__version_ext_names`（EXTENDED_MODVERSIONS），按符号名把模块期望 CRC 改成目标内核的值。对 `CGROUP_DEVICE=y` 的内核：

- 改写 404 个模块、共 6,377 条 CRC（`system_dlkm` 3,940 + `vendor_dlkm` 2,437）；
- 重新跑 gate：**CRC 不符 0 条**（未解析导入仍是 62 个模块，与 CRC 无关）；
- 模块签名因改写失效，但本内核 `MODULE_SIG_FORCE` 未开，可加载（会 taint）。

**真实风险用 BTF 量过了**：与 OS4 原厂内核比结构体布局——

| 类型 | 原厂 | out618s（同配置） | out618_cdev（+CGROUP_DEVICE） |
| --- | --- | --- | --- |
| `css_set` | 472 | **472** | **496**（+24） |
| `task_struct` | 4736 | 4736 | 4736 |
| `cgroup_subsys_state` | 216 | 216 | 216 |

基线布局完全一致；开启 device 控制器后 `css_set` 多出 3 个指针（`CGROUP_SUBSYS_COUNT` 变化）。所以补丁后的模块能过 CRC、能加载，但凡是直接触碰 `css_set` 数组的模块（多为 cgroup 相关内核内部代码，业务驱动很少）存在布局风险，必须真机验证，不能当日用方案。

## 6.18 线剩余缺口

1. Rust 工具链（rustc 1.91 / 15551131），恢复 `CONFIG_RUST`，解决 `rust_binder.ko` 的 60 个符号；
2. OS4 `vendor_boot` 模块，解决 62 个模块的 vendor-core 符号（`memcpy_s`、`cdev_tevent_*`、`vote_mng_*`、`walt_*`）。

## 用工作区里的完整 OS4 包重跑（2026-11-09 晚）

工作区里确实有干净的 OS4 完整包：`<workspace>/outputs/os4-ota-20261109/`（OTA zip + payload 解包出的 images，另一条会话今天上线的产物；设备现在就跑在 OS4/slot b）。从里面取：

- `vendor_boot.img` → 139 个 .ko（vermagic `6.18.21-android17-5-maybe-dirty-4k`）；
- `vendor_dlkm.img` → 194 个；`system_dlkm.img` → 210 个；`odm_dlkm.img` → 0 个 .ko。

用三组模块导入符号的并集（4,945 个）重建白名单，保持 stable 模式重编（`out618s2/`，导出 3,568 个符号），再跑 gate：

- 模块 543 个；**CRC 不符 0 条**；
- 无法解析导入只剩 **3 个模块**：
  - `wwan_gpio_pwrctl` 缺 `mtk_pwrctl_slt_gpio_init/uninit`（2 个）
  - `xr_pmonitor` 缺 `lp_mnt_counter_*`、`lp_mnt_set`、`next_op_mode`（4 个）
  - `rust_binder` 缺 60 个 Rust 符号（`CONFIG_RUST` 因本地无 rustc 被关）

前两类是厂商内核补丁（AOSP 树里没有 `lp_mnt`、`mtk_pwrctl_slt_gpio` 的实现），第三类是工具链问题（补 Android Rust 15551131 后可解）。也就是说 **6.18 线在 ABI 层面已经对齐到 540/543 个模块**。

## 弱引用修正与最终缺口（2026-11-09 晚）

`wwan_gpio_pwrctl` 的 `mtk_pwrctl_slt_gpio_init/uninit` 其实是 **weakref**（`nm` 类型 `w`），V 树源码里就是 `__attribute__((weakref(...)))`；弱引用缺失不影响加载。回归门因此改为只统计强未定义符号（`U`），重跑 543 个模块：

- CRC 不符 **0**；
- 未解析只剩 2 个模块：`xr_pmonitor` 缺 `lp_mnt_*`/`next_op_mode` 4 个（`U`，强引用，真实需求）、`rust_binder` 缺 60 个 Rust 符号。

`lp_mnt` 是强引用且 OTA 模块里没有提供方，说明它来自厂商内核内置代码（AOSP 树没有）；设备在线时用 `/proc/kallsyms` 可以确认地址并反汇编。Rust 工具链这边，`prebuilts/rust` 的 `android17-release` 只有 bootstrap、`main` 只有 1.82/1.83，还没找到 1.91.1（build 15551131）的 linux-x86 目录，需要按 build id 找对应分支。

## lp_mnt 结案：死模块，不用逆向（2026-11-09 深夜）

用 `vmlinux-to-elf`（虚拟环境装 `peewee`）从 OS4 内核 Image 恢复了 145,451 个符号，`nm | grep lp_mnt` 为空——**内核里根本没有这些符号**。再查 OTA：

- `vendor_boot` 里 `extra/xring-modules/drivers/l3/lp_mnt` 是**空目录**（没有 .ko）；
- `vendor.img`/`mi_ext`/`odm`/`product`/`system_ext` 全部分区都搜不到 `lp_mnt_set`；
- 设备上 `lsmod` 显示 `xr_pmonitor` **没有加载**（只有 `binder_gki`、`millet_binder`、`rust_binder` 等）。

所以 `xr_pmonitor` 是一个"有强引用但依赖的模块不存在"的模块，Android 启动时加载失败被跳过，属于死模块；`lp_mnt` 不值得逆向，回归门里把它当已知缺失处理即可。

## rust_binder：唯一还在的缺口

设备上 `rust_binder` 是加载状态（405,504 B），说明原厂内核带 Rust 支持；我们的纯 kbuild 因没有 rustc 把 `CONFIG_RUST` 关掉了。`prebuilts/rust` 的 `android17-release` 只有 `bootstrap`、`main` 只有 1.82/1.83，还没找到 1.91.1（build 15551131）的 `linux-x86` 目录，需要用 build id 对应的分支/镜像再查，或用发行版 rustc + bindgen 做实验（Rust 符号 CRC 可能不同，届时可用 CRC 补丁对齐）。

## 结论

OS4（6.18.21）自编内核在 ABI 层面已经能覆盖 542/543 个会加载的模块；`xr_pmonitor` 是死模块，`rust_binder` 只差工具链。设备当前运行 OS4/slot b，具备真机验证条件（需单独授权）。

## Rust 实验（2026-11-09 深夜）

用发行版工具链试了一次：`rustc 1.99.1` + `rust-src` + `rust-bindgen 0.73.2`（`pacman` 装的，`prebuilts/rust` 里没找到 1.91.1 的 linux-x86）。`olddefconfig` 能识别并保留 `CONFIG_RUST=y`（`RUST_IS_AVAILABLE=y`、`RUSTC_VERSION_TEXT` 正常）。

构建过程中遇到两处发行版 rustc 与 Android 工具链的差异，做了两处本地改动（都在源码副本里，已记录）：

1. `scripts/Makefile.autofdo` 的 `RUSTFLAGS_AUTOFDO_CLANG` 包含 `-Zdebug-info-for-profiling`，发行版 rustc 不认，改为空（Rust 侧不启用 AUTOFDO）。
2. `CONFIG_WERROR=y` 下 `rust/kernel/str.rs` 的 `flags::*` 被判 unused import 直接报错，本地实验关掉 WERROR。

改完后 `vmlinux` 构建成功（exit 0），但 **`vmlinux.symvers` 里没有任何 Rust 符号**：Rust 的 `exports_*.h` 是由使用方模块的集合生成的，只编 vmlinux（`KBUILD_MODULES=`）时不会导出。gate 仍然是 543 模块、CRC 0、未解析 2 个（`xr_pmonitor` 死模块 + `rust_binder` 58 个）。

要让 `rust_binder` 通过，下一步需要：`CONFIG_ANDROID_BINDER_IPC_RUST=y` 且按模块集一起构建（不能再用 `KBUILD_MODULES=` 跳过），这会拉长构建时间；考虑到设备上 `rust_binder` 的 refcount 是 0（没有使用方），优先级不高。

## Rust 完整构建结果：符号名哈希对不上（2026-11-09 深夜）

启用 `CONFIG_ANDROID_BINDER_IPC_RUST=m` 后按完整模块集构建（`make -j16`，stable 模式），`make` exit 0，产出 105 个模块、`Module.symvers` 里出现 56 个 Rust 导出符号（`_RNvNtCsjHhaP4e7D02_4core...`，`EXPORT_SYMBOL_GPL`）。

但 gate 依然把 `rust_binder` 列为缺 51 个符号，原因不是没导出，而是 **Rust 符号名里的 crate 哈希不同**：原厂用 Android rustc 1.91.1 编出 `CsdfZWD8DztAw`，发行版 1.99.1 编出 `CsjHhaP4e7D02`，`_RNv...` 名字整体不匹配。Rust 的 crate disambiguator 由编译器版本/源码哈希决定，不换到同一个工具链就无法对齐。

所以：
- `rust_binder` 只能等 Android Rust 1.91.1（build 15551131）的预编译找到；
- 它在设备上 refcount 0（没有使用方），可以接受缺失；
- 其余 542/543 个会加载的模块 CRC 全部对齐，`xr_pmonitor` 是死模块。

结论：OS4（6.18.21）的自编内核在"能加载的模块"范围内已经 ABI 完整，剩下的 `rust_binder` 属于工具链精度问题，不影响日常功能面。

## Android Rust 1.91.1 追查结果（2026-11-09 深夜）

- 内核 `bazel/constants.scl` 里写的是 `RUSTC_VERSION="1.91.1.p3"`，但 `prebuilts/rust` 公开分支里没有：
  - `android17-release` / `android17-security-release`：根目录只有 `bootstrap`、`tests`，**完全没有 `linux-x86`**；
  - `android16-release`：`linux-x86` 只有 `1.82.0`、`1.83.0`、`stable`；
  - `android16-qpr2-release`：只有 `1.88.0`、`stable`；
  - 直接探测 `linux-x86/1.91.1`、`linux-x86/1.91.1.p3` 在 main/android17-release/android16-release 都是 404；tags 里没有对应构建号 15551131。
- GitHub 上没有 `aosp-mirror/platform_prebuilts_rust` 镜像。

结论：**Android Rust 1.91.1.p3 目前没有公开的预编译**，`rust_binder` 的 crate 哈希（`CsdfZWD8DztAw`）无法用发行版 rustc 复现。`rust_binder` 在 OS4 上 refcount 为 0，属于可接受的缺口；等 Google 把 1.91.1.p3 推到公开 prebuilts 后再补即可，届时只需重编内核、gate 应自动归零。
