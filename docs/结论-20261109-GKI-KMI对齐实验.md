# 结论 2026-11-09（2026-11-10 重做并更正）：GKI/KMI 对齐实验

一句话：**保持原厂配置重编，导出符号集与 CRC 9,090/9,090 完全一致，KCFI 836/836 相同——"开源 ACK/GKI + 原厂闭源模块"这条路在离线层面已经走通；上一版"路线不成立"是构建偏差（关掉了 DEBUG_INFO/BTF）造成的假阴性，已撤回。**

## 实验设置

```
源码   <home>/ack-66118/src（ACK 6.6.118，GKI + xiaomi_xring KMI 列表 2,833 条）
config 设备 /proc/config.gz 原始导出（config.device，sha256 6fa1a889…）
工具链 <home>/clang-prebuilts/linux-x86/clang-r510928（Android (11368308) clang 18.0.0，
       与设备 CONFIG_CC_VERSION_TEXT 逐字一致）
命令   make -C <src> O=out ARCH=arm64 LLVM=1 olddefconfig            → 0
       make -C <src> O=out ARCH=arm64 LLVM=1 -j16 vmlinux           → 0（1m49s，user 22m）
产物   out/vmlinux 47,503,208 B；out/vmlinux.symvers 16,582 条
```

配置只允许四类改动：关 `DEBUG_INFO`（换 `DEBUG_INFO_NONE`，纯为提速；CRC 由 genksyms 在预处理阶段生成，与调试信息无关）、关 `TRIM_UNUSED_KSYMS`（让导出符号集覆盖原厂）、关 `MODULE_SIG_PROTECT`（排除签名干扰）、其余保持设备原值（`MODVERSIONS=y`、`CFI_CLANG=y`、`LTO_NONE=y`、`MODULE_SIG=y`）。

需要记下的意外差异：`F2FS_VIP_FILE`、`SCSI_DISCARD`、`SCSI_FASTDISCARD`、`XIAOMI_ENHANCED_IOSTAT`、`XIAOMI_EROFS_IOSTAT`、`MODULE_ALLOW_BTF_MISMATCH`、`UAPI_HEADER_TEST` 这些设备配置里的选项在本源码树里**不存在对应 Kconfig**，`olddefconfig` 后直接消失。这本身就是"源码不等于厂商 B 树"的信号。

## 判定结果

| 判据 | 结果 |
| --- | --- |
| 原厂导出符号覆盖 | 9,090 / 9,090 全部导出（关 TRIM 后 16,582 个） |
| symbol CRC 一致 | 2,115 / 9,090 = **23.3%**；6,975 个不同 |
| KMI 列表（2,833 条）覆盖 | 2,819 个导出，缺 14 个（`arc4_*`、`hci_*`、`rfkill_*`，属 GKI 模块导出） |
| KMI 符号 CRC 一致 | 767 / 2,819 = 27.2%；2,052 个不同 |
| KCFI 类型 id | 模块与内核共有 65 个 `__kcfi_typeid_*`，值不同 **0 个** |
| 原厂模块符号需求 | 201 个 .ko 中 63 个有缺符号（`mdr_*`、`cdev_tevent_*`、`dpu_wfd_*`、`ap_ipc_send_sync`、`get_hw_id_value` 等 vendor-core 层） |

关键交叉校验：直接读原厂 `mac80211.ko` 的 `__versions` 段（319 条），其中 213 条与原厂 `Module.symvers` 完全一致、只有 107 条与本内核一致——证明原厂符号表可信，CRC 差异不是恢复错误，而是**内核侧真的算出了不同的类型签名**。样例：`consume_skb` 模块要求 `21ee9387`、原厂表同值、本内核 `388ba9a2`；`_dev_info` 要求 `2137b691`、本内核 `523e56c6`。

## 怎么读这个结果

- CRC 是 genksyms 对导出符号原型里涉及的**类型**做的哈希。2/3 以上对不上，说明厂商在 B 版里改了大量被导出函数原型引用到的头文件（vendor hook、结构体字段、config 门控），不是"编译参数没对齐"这种量级的问题。
- KCFI 65 个样本 0 差异，说明 CFI 这一层至少在部分符号上是对齐的；但它排在 CRC 之后，CRC 不过，模块在 `check_version()` 阶段就被拒，CFI 根本轮不到。
- 63 个模块缺的 `mdr_*`、`cdev_tevent_*`、`dpu_wfd_*` 是 vendor-core 层的导出符号，原厂把它们放在 `vendor_boot` 的模块里（我们只比了 `vendor_dlkm` 的 201 个 .ko），所以这类缺失不代表最终结论，只说明分层：vendor-core 在 vendor_boot、业务驱动在 vendor_dlkm。

## 下一步（按代价排序）

1. **量化"补丁能否补齐"**：把 OSS V 树里 `kernel/`、`xiaomi-modules/`、`xring-modules` 的补丁与头文件改动，往 ACK 6.6.118 上移（V 与 B 只差 6.6.30→6.6.118，机制已证同源），每移一批重编一次，看 CRC 匹配率曲线。若能从 23% 爬到接近 100%，说明 B = GKI + 可复现的厂商补丁集，这条路仍可救；若爬到 60% 就停住，说明还有未公开改动，此路作废。
2. **GPL 源码请求**：正式渠道要 B 版源码；同期查 Software Heritage / Gitee / GitCode 镜像与同 SoC 机型。
3. **不依赖内核的替代**：`CGROUP_PIDS`/`PID_NS` 这类需求改到用户态或运行期模块解决；内核保持 stock。

## 局限

- 关 `DEBUG_INFO` 不影响 CRC（genksyms 在预处理阶段工作，已在上文说明），但会让 `pahole`/BTF 相关产物缺失；若要同时验证 BTF 需重开。
- KCFI 样本只有 65 个共有 typeid，未做全量遍历（模块侧 typeid 数量远大于内核导出的交集）。
- 未跑 `make modules`，因此"模块互相导出的符号"只从原厂 .ko 反推，未与本内核的模块侧导出交叉验证。
- 构建产物在 `out/`（约 1 GB），实验目录整体可清理，不影响其他产物。

## 重做实验（2026-11-10）：原厂配置 → CRC 100%

上一轮 23.3% 的假阴性已经查清并复现，原因不在厂商私有补丁，而在我们自己的构建偏差。

### 关键结果

| 构建 | 配置差异 | 导出 | 与原厂交集 | CRC 相同 |
| --- | --- | --- | --- | --- |
| out | 关 DEBUG_INFO/BTF、关 TRIM、关 MODULE_SIG_PROTECT | 16,582 | 9,090 | 2,115（23.3%） |
| **out2** | **原厂配置，仅把 UNUSED_KSYMS_WHITELIST 换成原厂 9,090 符号清单** | **9,090** | **9,090** | **9,090（100%）** |
| out3 | 同 out2，但关 TRIM | 16,583 | 9,090 | 9,090（100%） |
| out4/out5 | 同 out3，只关 DEBUG_INFO/BTF（含干净目录重编） | 16,582 | 9,090 | 2,115（23.3%） |
| out7_pidns | out2 + `CONFIG_PID_NS=y` | 9,090 | 9,090 | 9,090（100%） |
| out7_cgpids | out2 + `CONFIG_CGROUP_PIDS=y` | 9,090 | 9,090 | 5,948（65.4%） |

### 根因：`__user` 的 btf_type_tag 注解

`include/linux/compiler_types.h:11-16`：

```c
#if defined(CONFIG_DEBUG_INFO_BTF) && defined(CONFIG_PAHOLE_HAS_BTF_TAG) && \
	__has_attribute(btf_type_tag) && !defined(__BINDGEN__)
# define BTF_TYPE_TAG(value) __attribute__((btf_type_tag(#value)))
```

关掉 `DEBUG_INFO`/`DEBUG_INFO_BTF` 后，`__user` 从 `__attribute__((btf_type_tag("user")))` 退回空注解；genksyms 把属性算进类型字符串，于是所有含 `__user`（以及 `__iomem`/`__percpu`）的导出原型 CRC 全变。实测同一文件的 genksyms 输入差异就是 `void __attribute__((btf_type_tag("user"))) *to` 对 `void *to`。**这正是"一个公共注解变化连带改掉上千个 CRC"的现实例子**，也说明 CRC 只能当诊断指标。

### 完整模块集与 KCFI

- 模块 586 个（OS3 `vendor_boot` 385 + `vendor_dlkm` 201）；内核导出 9,090，模块导出 3,044，并集 12,134。
- 无法解析导入的模块只有 2 个（两份 `wwan_gpio_pwrctl`，缺 `mtk_pwrctl_slt_gpio_init/uninit`，推测在本地没有的 `system_dlkm`）。
- 模块 `__versions` 与原厂内核表 CRC 不一致条目：0。
- KCFI：模块与内核共有 836 条 `__kcfi_typeid_*`，值不同 0。仍是样本级验证，不等于所有间接调用通过。

### 功能开关的实际影响

`PID_NS=y` 对 ABI 无影响（CRC 仍 100%）。`CGROUP_PIDS=y` 会插入 `pids_cgrp_id` 到 `enum cgroup_subsys_id`（`include/linux/cgroup-defs.h`，由 `cgroup_subsys.h` 顺序决定），后续子系统 ID 整体后移；干净重编后 3,142 个导出符号 CRC 改变（65.4%），模块加载会失败。genksyms 输入差异已定位到这三处新增（enum 成员、extern subsys、static key）。

### 结论

- "开源 GKI/ACK + 原厂模块"在**保持原厂配置**时是可行的：离线已复现导出符号集与 CRC 完全一致。
- 之前"路线不成立"的判断是构建偏差导致的假阴性，撤回。
- 加功能要逐项验证：`PID_NS` 安全；`CGROUP_PIDS` 目前不安全，需要先解决 enum 顺序（例如把 pids 子系统追加到末尾而不是插在中间）再验证，或改用其它实现路径。
- 尚未做真机启动/模块加载验证；这一步需要单独授权。

## 追加实验：CGROUP_PIDS 的枚举顺序补丁（2026-11-10）

在 6.6.118 副本里把 `SUBSYS(pids)` 从 `include/linux/cgroup_subsys.h` 中间挪到末尾（保持已有子系统 ID 不变），用原厂配置 + `CGROUP_PIDS=y` 重编（out8，干净目录，exit 0）。结果：

- 全量符号 CRC 仍是 **5,948 / 9,090 = 65.4%**，与未打补丁的 out7_cgpids 完全相同（9,090 个交集里 3,142 个不同），枚举顺序不是主因。
- 改用**模块实际导入的符号**做判据（更贴近真实加载）：586 个模块的 `__versions` 共 28,356 条内核符号期望值——out2 基线 **0 条不符**；out7/out8 均 **7,027 条不符**（`get_device`、`put_device`、`__root_device_register`、`snd_soc_register_card` 等）。模块加载时会直接拒绝。

结论：在这个内核上直接打开 `CGROUP_PIDS` 会破坏模块 ABI，靠调整枚举顺序救不回来；要拿到 pids 控制器，只能换别的实现路径（例如随模块一起重编整套、或以 LKM 方式旁路），不能只改 config。

判定方法也就此定下来：**以"模块 __versions 与实际内核导出 CRC 的差异条数"为主判据**（基线 0），全量 CRC 百分比只作诊断。
